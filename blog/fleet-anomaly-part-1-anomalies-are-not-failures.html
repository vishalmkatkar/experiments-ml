Anomalies Are Not Failures

Unsupervised models find unusual behavior. Logs and service history turn it into a diagnosis and a service action. An architecture for doing both across a fleet of machines.

12 min readFor ML and data engineers building predictive maintenance

Most anomaly detection projects end at a score. A model learns what normal sensor readings look like, flags what doesn't fit, and sends an alert. Then someone on the maintenance team opens it and has to answer three questions the model never asked: is this a real problem, what is going wrong, and what should we do about it? When the answer to the first question is "no" too often, people stop opening the alerts.

This series builds the rest of that path. It starts with unsupervised detection on sensor telemetry, links what it finds to error logs and failure events, and ends with a recommended service action drawn from what fixed similar cases before. It runs on Apache Spark, tracks models in MLflow, and every part ships with runnable reference code on a synthetic fleet whose ground truth lets each claim be measured.

This first part covers the design: the problem, the data, the pipeline, where each tool fits, and how the results will be judged. The later parts take one stage each.

The problem

Three facts about industrial fleets shape everything below.

  1. Most alerts are mode changes.

    A compressor at peak load runs hotter and vibrates more than the same compressor idling. A machine starting up looks nothing like one in steady state. A detector that learns one fleet-wide "normal" flags every startup, every peak shift and every machine that simply runs harder than average. These alerts are correct about the statistics and useless to the people who receive them.

  2. Failures are rare and badly labelled.

    A well-run fleet sees a handful of real failures per machine per year, often fewer. That is too few to train a classifier per failure mode, and the labels that exist are noisy: the failure date is when someone logged it, not when the fault began. This is why the detection itself has to be unsupervised.

  3. What fixed the problem is buried in free text.

    Service records hold the most useful history in the business: what the technician found, what they replaced, and whether the machine came back a week later. Most of it is typed into a notes field, in different words by different people.

An anomaly answers "is this unusual?" A failure answers "what is breaking?" A service action answers "what should we do?" They need different evidence.

Three questions, three kinds of evidence

The architecture follows from keeping those questions apart. Each one is answered by a different technique, from a different data source, and each can be wrong in its own way.

QuestionEvidenceTechniqueTypical mistake
Is this unusual?Sensor telemetry, compared with the same kind of machine in the same operating modeClustering for profiles and modes; robust statistics, Isolation Forest and forecast residuals for detectionFlagging a normal mode change as an anomaly
What is going wrong?Error codes, failure events and past episodes with known outcomesCorrelation, time-window joins, association rules, nearest-neighbor matching on episode signaturesNaming a failure mode on an episode that never led to one
What should we do?Service records: actions taken, parts used, whether the fix heldCase similarity, collaborative filtering, ranking by first-time fix rateRecommending the action tried most often instead of the one that worked

A system that answers only the first question is a monitoring tool. A system that answers all three, and says how confident it is in each answer, is something a maintenance planner can act on.

The data

Five sources, at very different grains. Telemetry is dense and regular. Everything else is sparse, irregular and recorded by people or by controllers with their own idea of time.

SourceGrainKey fieldsShapeUsed in
TelemetryMachine × hourmachine_id, ts, six sensors such as vibration, temperature, pressure and motor currentDense. The test fleet: about 200 machines × 8,760 hours ≈ 1.75 million rowsParts 2–5
Error logsEventmachine_id, ts, code, severitySparse and noisy. Many codes have nothing to do with failuresParts 4–5
Failure eventsEventmachine_id, ts, component, failure_modeRare. Timestamped when logged, not when the fault beganParts 4–5

Machine metadataMachinemodel, site, install_date, rated capacitySmall and slowly changingPart 2

The join keys look simple, machine_id and time, but time is where these sources disagree. A failure logged at 09:00 on Tuesday may have started on Sunday night. So the pipeline never joins on exact timestamps. It joins anomaly episodes to events within windows, and Part 4 measures how wide those windows need to be for each failure mode.

The pipeline

Five stages, each with one job, connected by a feedback loop from the technicians who act on the output.

1Profile: define normal per kind of machine and per mode

Before anything can be called abnormal, the system needs to know what normal is for this machine, right now. Two clustering steps provide that. The first groups machines into profiles from summary features: typical sensor levels, variability, duty cycle and how the sensors move together. Machines of the same nominal model often end up in different profiles because they do different work. The second step clusters time windows within each profile into operating modes such as idle, normal load, peak and startup.

k-means and Gaussian mixtures do the grouping. HDBSCAN plays a different role: it leaves points that fit no cluster unassigned, which is how the pipeline finds machines that match no profile at all. Those go to a person, not to the detector. Part 2 covers how to choose the number of clusters (silhouette score plus stability across resampled fleets) and what to do when a machine changes profile after a service visit.

2Detect: score against the right baseline, alert on episodes

Detection runs per profile and per mode. The baseline is deliberately simple: a robust z-score per sensor, using the median and the median absolute deviation of that profile and mode, so a few extreme readings in the history don't stretch the definition of normal.

python · sketch 
def robust_z(df, sensors):
    # Normal is defined per profile and operating mode, never fleet-wide.
    keys = [df["profile"], df["mode"]]
    median = df[sensors].groupby(keys).transform("median")
    mad = (df[sensors] - median).abs().groupby(keys).transform("median")
    return (df[sensors] - median) / (1.4826 * mad + 1e-9)

On top of that baseline sit two models that see what a per-sensor score cannot. Isolation Forest, one per profile, catches unusual combinations of values that are each normal on their own. Forecast residuals catch unusual sequences: a temperature that should have fallen after a load drop and didn't.

Two rules then turn scores into alerts. Scores are calibrated per machine, as percentiles of that machine's own history, so one noisy machine cannot flood the queue. And alerts are raised on episodes, not points: consecutive anomalous windows are merged, an episode must last a minimum time, and a cool-down stops the same episode from alerting twice. Part 3 builds all of this and measures how many alerts mode-aware baselines remove.

3Correlate: relationships, then logs

Correlation does two separate jobs here. The first is a second detection signal. Sensors on a healthy machine move together in stable ways: motor current tracks load, temperature follows current with a lag. Slow degradation often shows up as those relationships weakening while every individual value still sits inside its normal range. A correlation-break score measures how far a machine's recent correlation matrix has drifted from its profile's normal one.

The second job is giving an anomaly meaning. Episodes are joined to error codes and failure events that follow within a time window, and association rules over those joins show which episode types and codes tend to precede which failures, with support, confidence and lift. The same joins produce the lead time for each failure mode: how many days before a failure its warning signs appear. That number decides how urgent an alert is, and it also produces the weak labels Part 5 trains on.

4Diagnose: which past episodes does this one resemble?

With too few failures to train a classifier per failure mode, diagnosis works by similarity. Each episode gets a signature: which sensors deviated and in which direction, the shape of the deviation over time, which correlations broke, and which error codes appeared alongside it. A new episode is compared with past episodes whose outcome is known. If its nearest neighbors mostly ended in bearing failures, the likely mode is a bearing failure, and the share of neighbors that agree is the confidence.

This approach has a useful property: every diagnosis comes with its evidence, the specific past episodes it matched. Part 5 also trains a supervised model on the weak labels from Part 4 and compares the two honestly, using time-based splits only.

5Recommend: what fixed similar cases, not what was tried most

The last stage ranks service actions. A naive recommender suggests whatever technicians did most often for this failure mode, which reproduces existing habits, including the bad ones. This one blends three signals: similarity to past cases, collaborative filtering (ALS) over machines and actions with fix outcomes as feedback, and a ranking weighted by first-time fix rate, so an action that usually needed a second visit within 30 days ranks below one that held.

The output is a short ranked list with the past cases behind each entry. Technicians confirm or reject it, and that feedback becomes new labels for correlation and diagnosis and new outcomes for the recommender. That loop is what lets the system improve without anyone running a labelling project.

The episode record

The stages communicate through one object: the episode. Detection creates it, each later stage adds to it, and it is what a person finally reads. Defining it up front keeps the stages independent and makes every decision traceable back to the readings that caused it.

{
  "episode_id": "ep-0412",
  "machine_id": "M-117",
  "profile": "P2", "mode": "normal_load",
  "start": "2026-03-04T02:00", "end": "2026-03-06T19:00",
  // Detect
  "score_pct": 0.997,
  "deviations": {"vibration": "+4.1 MAD, rising", "temperature": "+2.3 MAD"},
  // Correlate
  "broken_pairs": [["current", "temperature"]],
  "codes": ["E214", "E214", "E031"],
  // Diagnose
  "likely_mode": "bearing_wear", "confidence": 0.7,
  "similar_episodes": ["ep-0087", "ep-0233", "ep-0301"],
  "typical_lead_days": 9,
  // Recommend
  "actions": [
    {"action": "replace_bearing", "first_time_fix": 0.86, "cases": ["sv-1190", "sv-1342"]},
    {"action": "lubricate_and_recheck", "first_time_fix": 0.41, "cases": ["sv-0977"]}

}

The values above are made up to show the shape. Every field after deviations is optional: an episode with no matching history stops at "unusual, no known cause", and the record says so instead of guessing.

Spark and MLflow

The fleet is large in one dimension (telemetry) and small in all the others. That decides where Spark earns its place. It does the fleet-wide window features, the per-profile training, the time-window joins against logs, and the two algorithms MLlib provides directly: ALS for recommendation and FP-Growth for association rules. The models themselves are mostly scikit-learn, trained inside Spark groups.

def fit_profile(pdf: pd.DataFrame) -> pd.DataFrame:

MLflow tracks every clustering setup and detector as a run, with its metrics and evaluation report as artifacts. The per-profile detectors are registered as one model behind a single scoring wrapper that routes each window to its profile's detector, so the rest of the pipeline sees one model. Aliases manage promotion: scoring always loads models:/fleet-detector@champion, a new version is registered as challenger, and it is promoted only after it beats the champion on the measures below.

Everything in this series runs on one laptop, with Spark in local mode. The code is the same code a cluster would run, and the test fleet is sized so Spark does real work. The posts will say plainly where it ran.

Where the LLM fits

After three posts about LLM systems, this one gives the LLM a deliberately small role. The deterministic agents post argued that code should own every decision that doesn't need judgment; in this pipeline, that is almost all of them.

No LLM

Profiling, detection, correlation, diagnosis and ranking. These are numeric problems with good statistical tools, and they need to be fast, cheap, repeatable and explainable. An LLM adds none of that.

LLM

Reading free-text service notes into a consistent failure mode, action and parts list. Drafting the work order from the episode record, citing the past cases it used, the same pattern as the citations in the RAG post.

The LLM works on text that people wrote and text that people will read. It never decides whether a machine is behaving abnormally, and it can't invent a recommendation: it only writes up what the ranking stage produced.

How it will be measured

Anomaly detection is easy to make look good. Point-wise accuracy is near 100% for a model that never alerts, because almost every hour is normal. The widely used point-adjusted F1 is worse: if any point inside a true anomaly segment is flagged, every point in that segment counts as detected, and on long segments even random scores can reach a high F1 (Kim et al., AAAI 2022). Neither tells a maintenance team anything.

This series reports four measures instead, each tied to a decision someone makes:

MeasureDefinitionThe question it answers
Precision within an alert budgetFix how many alerts the team can handle per week; of the top-ranked episodes within that budget, the share that were realIs the team's time well spent?
Event recallShare of failures with at least one alert in a window before the failure; alerts after the failure don't countHow many failures did we see coming?
Lead timeMedian time between the first correct alert and the failure, per failure modeIs there time to plan the repair?
First-time fix rateShare of recommended actions where the fix held, with no repeat visit within 30 daysDid the recommendation work?
Leakage traps

Two mistakes inflate every result in this field. Random train and test splits let a model learn from the future, so every split here is by time. And features that encode a maintenance visit (a reset counter, a sudden drop in vibration after new parts) let a model "predict" the repair that already happened. Those features are kept out of training.

The test bench

Every measure above needs ground truth, and real fleets don't come with it. So the reference code starts with a generator for a synthetic fleet that does:

  • About 200 machines in four hidden profiles, with hourly readings from six sensors for one year.
  • Operating modes that shift by schedule and load.
  • Four failure modes, each with its own signature: which sensors drift, which relationships break, and a typical lead time.
  • Sudden faults alongside slow degradation.
  • Noisy error logs, and service records with free-text notes, actions, parts and whether the fix held.
  • A ground-truth file with the true profiles, anomaly windows, failure causes and the correct action for each case.

Synthetic data flatters results, so each part states that limit and adds realistic noise, and the pipeline will also be checked on a public predictive-maintenance dataset with real telemetry, errors, maintenance and failures. The measured numbers start in Part 2.
